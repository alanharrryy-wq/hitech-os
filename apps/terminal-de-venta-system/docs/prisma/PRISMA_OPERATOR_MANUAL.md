# PRISMA Operator Manual

Run timestamp: 2026-05-11T01:55:09.6153907-06:00

## Operational Law

PRISMA product law is:

- Tablet operates.
- PC governs.
- Mobile supervises.
- Core records through the Prisma ORM governed canonical database flow.
- Control audits.

The primary operational path is Tablet offline-first sale, semantic outbox event, PC ingest, Prisma ORM projector, canonical database state, Mobile snapshot, and Control audit.

The TRI-DB bridge is not the normal sync path. It is rescue/backfill/diagnostic tooling only.

## Offline Rules

- Tablet must never require PC connectivity to sell.
- Pending events are allowed while offline.
- Failed/conflict events must remain visible.
- A received event is not reconciled until validation/projection/reconciliation has evidence.
- `acked` is compatibility wording only when mapped to documented lifecycle evidence.

## Bridge Rules

Use:

```powershell
python tools/prisma/tri_db_bridge.py --self-test
```

Allowed bridge purposes:

- rescue
- backfill
- diagnostics
- migration assistance
- constraint inspection
- emergency projection
- self-test harness

Forbidden bridge purpose:

- primary normal Tablet to PC sync architecture

## Mobile Supervision Rules

Mobile must read `/api/mobile/snapshot` or derived Mobile view models. Mobile must not mutate sales, cash, checkout, inventory, or canonical business records.

Runtime modes:

- `live`
- `partial`
- `offline`
- `stale`
- `unknown`
- `demo-disabled`

Missing or uncertain data must stay explicit as null, unknown, unavailable, partial, stale, offline, or demo-disabled. No fake production data should be introduced.
